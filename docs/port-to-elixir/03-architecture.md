# 03 — Current Architecture

> Part of the [Junius → Elixir/Phoenix report](README.md). As-is analysis, with concrete
> interfaces quoted from source. Paths are relative to the Rust repo root.

## 1. Compile-time plugin composition

Junius is a **compile-time plugin-driven monolith**. A deployment's `platform.toml` lists the
enabled plugins; the `junius` CLI's `sync` command reads it and **generates static wiring** —
there is no dynamic loading. Adding or removing a plugin is a rebuild.

The generated registry is the clearest illustration (`platform/src/generated/plugins.rs`,
verbatim):

```rust
// Generated by `junius sync` from <deployment>/platform.toml.
// DO NOT EDIT BY HAND. Re-runs of `junius sync` overwrite this file.

use junius_sdk::Plugin;

/// Constructed plugin registry, in deployment-declared order.
#[must_use]
pub fn plugins() -> Vec<Box<dyn Plugin>> {
    vec![
        Box::new(events_plugin::EventsPlugin::new()),
        Box::new(admin_plugin::AdminPlugin::new()),
    ]
}
```

`junius sync` also generates: `platform/src/generated/rpc_requires.rs` (an `RPC_REQUIRES` table
mapping `(service, method) → required permissions`, and an `RPC_SERVICES` map of
`service_fqn → owning plugin`), and the frontend's `routes.ts`, `component-registry.ts`, and
`i18n-catalogs.ts`. It maintains marker-delimited regions in `Cargo.toml`s, `buf.yaml`, and the
host frontend `package.json`.

**Port implication:** this entire generation step is replaced by a **runtime registry** in
Elixir — enabled OTP apps implementing a behaviour, discovered at boot. See
[05](05-elixir-target-architecture.md).

## 2. Request lifecycle

```
Request
  │
  ├─ tower_cookies::CookieManagerLayer
  ├─ correlation::stamp            (tracing span; x-correlation-id on response)
  ├─ auth::session::middleware     (session cookie → User into request extensions;
  │                                 non-rejecting — extractors enforce auth)
  │
  ├─ /api/auth/*                   (public: OIDC login/callback/logout)
  ├─ /api/me*, /h/<plugin>/*       (authed plain HTTP)
  └─ /rpc/*  (Connect-RPC), wrapped by, in order:
        1. rpc_guard::admin_token       → inserts AdminAuth marker on valid bearer
        2. rpc_guard::inject_ctx        → attaches the owning plugin's PluginResourceCtx
        3. rpc_guard::require_permissions → rejects PRE-DISPATCH on proto-declared `requires`
        → Connect handler → repository method → SQL (joins user_can_access)
```

Two independent permission enforcement points exist for RPC: the **host guard**
(`platform/src/rpc_guard.rs`, reading `RPC_REQUIRES`) rejects before the handler runs, and the
**handler's own witness** (`PluginContext::from_rpc`) re-checks at runtime. See
[04](04-plugin-interface.md).

## 3. Deployment topologies

- **Embedded SPA** — `rust-embed` bakes the Vite build into `juniusd` (feature
  `embed-frontend`); the binary serves `/assets/*` and an SPA fallback.
- **Headless + SSR** — `juniusd` returns a structured `FRONTEND_NOT_EMBEDDED` 404 on browser
  routes; a separate Node SSR server serves the FE and proxies `/api`, `/h`, `/rpc` to the
  backend, forwarding cookies + `Accept-Language` via `AsyncLocalStorage`.
- **Precompiled images** — `full` / `backend` / `frontend` variants on `ghcr.io`; the image sets
  `JUNIUS_MODE=precompiled` and a boot check refuses to start unless `[plugins].enabled` exactly
  matches the linked plugin set.
- **Source vs deployment split** — a deployment dir holds only `platform.toml` + secrets +
  `platform.lock` (blake3 hashes); `junius build` resolves the platform source by path or git
  rev.

## 4. Host data model (`platform.*` + `meta.*`)

The host owns identity, RBAC, ownership/sharing, audit, and bookkeeping. Quoted from
`platform/migrations/*.up.sql`.

### Identity & sessions

```sql
-- 0001_users.up.sql
CREATE SCHEMA platform;

CREATE TABLE platform.user (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    oidc_sub      TEXT NOT NULL UNIQUE,         -- Authentik subject
    email         TEXT NOT NULL,
    display_name  TEXT NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```sql
-- 0002_sessions.up.sql — the cookie carries only the session id; oidc_tokens is encrypted.
CREATE TABLE platform.session (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES platform.user(id) ON DELETE CASCADE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at    TIMESTAMPTZ NOT NULL,
    oidc_tokens   BYTEA                          -- encrypted, optional
);
```

### Groups, roles, memberships (per-group RBAC)

```sql
-- 0003_groups_roles_memberships.up.sql
CREATE TABLE platform.group (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name TEXT NOT NULL, description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE platform.group_role (            -- a role is scoped to a group
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    group_id UUID NOT NULL REFERENCES platform.group(id) ON DELETE CASCADE,
    name TEXT NOT NULL, UNIQUE (group_id, name)
);
CREATE TABLE platform.role_permission (       -- role → permission string, e.g. 'events:read'
    role_id UUID NOT NULL REFERENCES platform.group_role(id) ON DELETE CASCADE,
    permission TEXT NOT NULL, PRIMARY KEY (role_id, permission)
);
CREATE TABLE platform.group_membership (      -- one role per (user, group)
    user_id UUID NOT NULL REFERENCES platform.user(id) ON DELETE CASCADE,
    group_id UUID NOT NULL REFERENCES platform.group(id) ON DELETE CASCADE,
    role_id UUID NOT NULL REFERENCES platform.group_role(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, group_id)
);
```

Milestone M18 added a **global** role axis (`0013_user_roles.up.sql`): `platform.user_role`,
`user_role_permission`, and `user_role_assignment`. The built-in `admin` role holds the wildcard
permission `'*'`. `group_membership` also gained `managed_by` (`manual`/`oidc`/`config`)
provenance.

### Ownership & sharing (resource scope)

```sql
-- 0004_resource_principal_share.up.sql
-- Ownership: exactly one of user_id / group_id is set.
CREATE TABLE platform.resource_principal (
    resource_kind   TEXT NOT NULL,               -- '<plugin>:<table>', e.g. 'events:event'
    resource_id     UUID NOT NULL,
    owner_user_id   UUID REFERENCES platform.user(id)  ON DELETE CASCADE,
    owner_group_id  UUID REFERENCES platform.group(id) ON DELETE CASCADE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (resource_kind, resource_id),
    CHECK ((owner_user_id IS NULL) <> (owner_group_id IS NULL))
);
-- Explicit per-resource grants (to a user, a group, or the public).
CREATE TABLE platform.resource_share (
    resource_kind TEXT NOT NULL, resource_id UUID NOT NULL,
    principal_kind TEXT NOT NULL,                -- 'user' | 'group' | 'public'
    principal_user_id UUID REFERENCES platform.user(id) ON DELETE CASCADE,
    principal_group_id UUID REFERENCES platform.group(id) ON DELETE CASCADE,
    permission TEXT NOT NULL,
    granted_by_user_id UUID NOT NULL REFERENCES platform.user(id),
    granted_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ,
    CHECK ( /* exactly one principal per kind; public has neither */ )
);
```

Other host tables: `platform.audit_event`, `platform.oidc_group_mapping`,
`platform.provisioning_state`; and `meta.migrations`, `meta.job_run`, `meta.object`.

### Migration bookkeeping

```sql
-- 0006_meta_migrations.up.sql
CREATE SCHEMA meta;
CREATE TABLE meta.migrations (
    id              BIGSERIAL    PRIMARY KEY,            -- true apply-order
    plugin          TEXT         NOT NULL,               -- 'platform' for host migrations
    migration_name  TEXT         NOT NULL,               -- e.g. '0007_audit_event'
    checksum        TEXT         NOT NULL,               -- SHA-256 of .up.sql contents
    applied_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    UNIQUE (plugin, migration_name)
);
```

## 5. Two-layer authorization (the core security model)

Every authenticated request is subject to two independent layers:

**Layer 1 — capability gate (coarse RBAC).** "Does the user hold permission `X` in *some* group,
or via a global user-role?" In Rust this is enforced at compile time by type-level witnesses and
pre-dispatch by the RPC guard. The runtime check lives in `User::has_permission`
(`crates/junius-sdk/src/auth.rs`):

```rust
pub fn has_permission(&self, permission: &str) -> bool {
    self.is_admin()
        || self.user_roles.iter().any(|r| r.permissions.contains(permission))
        || self.memberships.iter().any(|m| m.permissions.contains(permission))
}
```

**Layer 2 — resource-scoped filter (fine-grained, per instance).** A single plpgsql function,
`platform.user_can_access`, is joined into *every* repository query. It answers "may this user
exercise this permission on this specific resource?" via ownership → group-role → user share →
group share → public share, with an **admin wildcard fast-path** on top. This is the
security-critical heart of the system and is **language-neutral — the port keeps it verbatim.**

Quoted from `platform/migrations/0013_user_roles.up.sql` (the current version, which adds the
admin fast-path over the M08 body):

```sql
CREATE OR REPLACE FUNCTION platform.user_can_access(
    p_resource_kind TEXT, p_resource_id UUID, p_user_id UUID, p_permission TEXT
) RETURNS BOOLEAN
LANGUAGE plpgsql STABLE
SECURITY DEFINER                              -- callable by least-privilege plugin roles
SET search_path = platform, pg_temp
AS $$
DECLARE
    v_owner_user_id  UUID;
    v_owner_group_id UUID;
BEGIN
    -- Step 0: admin fast-path. Any user-role assignment holding '*' bypasses the ACL.
    IF EXISTS (
        SELECT 1 FROM platform.user_role_assignment ura
        JOIN platform.user_role_permission urp ON urp.role_id = ura.role_id
        WHERE ura.user_id = p_user_id AND urp.permission = '*'
    ) THEN RETURN true; END IF;

    -- Step 1: resolve ownership.
    SELECT owner_user_id, owner_group_id INTO v_owner_user_id, v_owner_group_id
    FROM platform.resource_principal
    WHERE resource_kind = p_resource_kind AND resource_id = p_resource_id;

    -- 1a. Owner has implicit full access.
    IF v_owner_user_id = p_user_id THEN RETURN true; END IF;

    -- 1b. Group-owned and the user's role in that group grants the permission.
    IF v_owner_group_id IS NOT NULL AND EXISTS (
        SELECT 1 FROM platform.group_membership gm
        JOIN platform.role_permission rp ON rp.role_id = gm.role_id
        WHERE gm.user_id = p_user_id AND gm.group_id = v_owner_group_id
          AND rp.permission = p_permission
    ) THEN RETURN true; END IF;

    -- 2. Active explicit share to this user.
    IF EXISTS (
        SELECT 1 FROM platform.resource_share rs
        WHERE rs.resource_kind = p_resource_kind AND rs.resource_id = p_resource_id
          AND rs.permission = p_permission AND rs.principal_user_id = p_user_id
          AND (rs.expires_at IS NULL OR rs.expires_at > now())
    ) THEN RETURN true; END IF;

    -- 3. Active share to a group the user is in.  (JOIN group_membership on principal_group_id)
    -- 4. Active public share (principal_kind = 'public').
    -- … both identical in shape to step 2 …

    RETURN false;
END;
$$;
```

Companion **SECURITY DEFINER** functions let least-privilege plugin roles write the host authz
tables inside their own transaction (`platform/migrations/0008_authz_functions.up.sql`,
`0012_forget_resource.up.sql`):

```sql
CREATE FUNCTION platform.record_owner(
    p_resource_kind TEXT, p_resource_id UUID, p_owner_user_id UUID, p_owner_group_id UUID
) RETURNS VOID LANGUAGE plpgsql SECURITY DEFINER SET search_path = platform, pg_temp
AS $$ BEGIN
    INSERT INTO platform.resource_principal
        (resource_kind, resource_id, owner_user_id, owner_group_id)
    VALUES (p_resource_kind, p_resource_id, p_owner_user_id, p_owner_group_id);
END; $$;
-- platform.forget_resource(kind, id) clears resource_principal + resource_share (delete inverse).
```

**How a plugin uses Layer 2** — every read filters on `user_can_access`, and returns
server-computed `viewer_can_*` flags so the frontend never recomputes access. From
`plugins/events/src/repo/event.rs` (the `list` method):

```rust
sqlx::query!(r#"
    SELECT e.id, e.title, /* … */
      platform.user_can_access('events:event', e.id, $1, 'events:write') AS "viewer_can_edit!",
      platform.user_can_access('events:event', e.id, $1, 'events:share') AS "viewer_can_share!"
    FROM events.event e
    WHERE e.visibility = 'public'
       OR platform.user_can_access('events:event', e.id, $1, 'events:read')
    ORDER BY e.starts_at, e.id
"#, viewer)
```

Rows the user can't access simply don't appear — no mid-query "permission denied", no existence
leak. Public events short-circuit the ACL on read (a `visibility` column), which is how the
unauthenticated invite pages work.

## 6. Per-plugin schemas, roles & migrations

- **One schema + one least-privilege Postgres role per plugin** (`role_events`, etc.). A plugin's
  role gets DML only on tables it declares in `[exposes.tables]`. A privileged
  `platform_migrator` role runs migrations and issues grants. Role passwords are derived
  deterministically from a `role_password_secret`.
- **Migrations are up-only**, host-first, then plugin migrations **topo-sorted** over a DAG built
  from within-plugin filename order plus explicit `-- @requires <plugin>:<migration>` header
  directives. Example (`plugins/events/migrations/0001_event.up.sql`):

```sql
-- @requires platform:0001_users
-- @requires platform:0003_groups_roles_memberships
CREATE SCHEMA IF NOT EXISTS events;
CREATE TYPE events.visibility AS ENUM ('private', 'public');
CREATE TYPE events.owner_kind AS ENUM ('user', 'group');
CREATE TABLE events.event (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title TEXT NOT NULL CHECK (length(btrim(title)) > 0),
    /* … */
    visibility  events.visibility NOT NULL DEFAULT 'private',
    owner_kind  events.owner_kind NOT NULL,
    owning_user_id  UUID REFERENCES platform.user(id),   -- no cross-schema CASCADE (RESTRICT)
    owning_group_id UUID REFERENCES platform.group(id),
    CONSTRAINT event_owner_matches_kind CHECK ( /* exactly one owner per kind */ )
);
```

- Migrations are **always-applied**: every deployment migrates every plugin's schema regardless
  of which plugins are *enabled* (enable/disable is purely a code concern; the schema always
  exists).

## 7. Cross-plugin composition (as-is)

- `[exposes.tables]` is the SQL compatibility surface; a consumer declares
  `[dependencies.<dep>].tables` and may then read/write those tables directly via SQL (invariants
  enforced by Postgres triggers). Cross-plugin FKs must be nullable into optional deps and must
  not CASCADE.
- Frontend components are shared via a generated registry + `useComponent('events.EventCard')`.
  Each consumer gets a **narrow** generated RPC namespace exposing only its own methods plus
  declared cross-plugin methods.
- `junius check` statically enforces all cross-plugin rules (`SQL.PRIVATE_TABLE_ACCESS`, FK
  rules, `DEP.UNDECLARED`, `RPC.UNDECLARED`, breaking-change rules).

> The port **changes this model deliberately**: cross-plugin access moves from shared SQL tables
> to **context-function APIs** (see [05 §Cross-plugin](05-elixir-target-architecture.md) and
> [07](07-mapping-and-tradeoffs.md)), which is both more idiomatic and strictly safer.

## 8. Summary for the port

The architecture's **portable, language-neutral core** is: the Postgres data model, the
`user_can_access` / `record_owner` / `forget_resource` functions, per-plugin schemas + roles, the
up-only `@requires` migration model, and the two-layer authorization design. The **replaced**
parts are: compile-time composition (`junius sync` → generated registries), the Connect-RPC
transport, and the type-system machinery detailed in [04](04-plugin-interface.md).
