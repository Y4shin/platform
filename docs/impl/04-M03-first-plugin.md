# M03 — First Plugin (`hello`) + `junius sync` Wiring

## Goal

A trivial `hello` plugin lives under `plugins/hello/`. `junius sync` reads `dev/platform.toml`, generates `platform/src/generated/plugins.rs` listing every enabled plugin, and a rebuild produces a binary that serves `/h/hello/ping` returning `"pong"`. The end-to-end Rust-only path works.

## Why now

This is the smallest realistic exercise of the architecture: a plugin manifest, a Rust crate implementing `Plugin`, the `plugin_metadata!` macro round-tripping `plugin.toml` to a static metadata constant, and `junius` composing the host with the plugin registered. Every later milestone builds on this proof.

## Scope (in)

### `plugins/hello/`

```
plugins/hello/
├── plugin.toml
├── Cargo.toml
└── src/
    └── lib.rs
```

`plugin.toml`:

```toml
[plugin]
name = "hello"
display_name = "Hello"
description = "Smoke-test plugin exercising the platform shape."
manifest_schema = 1

# No [dependencies], [exposes], [permissions], [requires] yet.
# Mount prefixes default from `plugin.name`:
#   route_prefix = "/p/hello"
#   rpc_prefix   = "/rpc/hello"
#   http_prefix  = "/h/hello"
```

`Cargo.toml`:

```toml
[package]
name = "hello-plugin"
version = "0.0.0"
edition.workspace = true

[dependencies]
junius-sdk.workspace = true
axum.workspace = true
async-trait.workspace = true
```

`src/lib.rs`:

```rust
use axum::{routing::get, Router};
use junius_sdk::{Plugin, PluginMetadata, PluginResources};

junius_sdk::plugin_metadata!();

pub struct HelloPlugin;

impl HelloPlugin {
    pub fn new() -> Self {
        Self
    }
}

#[async_trait::async_trait]
impl Plugin for HelloPlugin {
    fn metadata(&self) -> &'static PluginMetadata {
        &METADATA
    }

    fn routes(&self, _resources: PluginResources) -> Router {
        Router::new().route("/ping", get(|| async { "pong" }))
    }
}
```

### `junius sync` implementation

`junius sync` walks the enabled plugins from `platform.toml` (M01 already parses this), then writes `platform/src/generated/plugins.rs`:

```rust
// Generated by `junius sync` — do not edit.
use junius_sdk::Plugin;

pub fn plugins() -> Vec<Box<dyn Plugin>> {
    vec![
        Box::new(hello_plugin::HelloPlugin::new()),
    ]
}
```

Plus updates `platform/Cargo.toml` between marker comments to add `path` deps on each enabled plugin crate:

```toml
[dependencies]
junius-sdk.workspace = true
# ... existing deps ...

# >>> junius managed start
hello-plugin = { path = "../plugins/hello" }
# <<< junius managed end
```

Implementation notes:
- Plugin enumeration order from `[plugins].enabled` is preserved (deterministic).
- `--dry-run` prints the diff that would be written, exits 0 if no change, 1 if a write would occur.
- Marker-comment editor lives in `tools/junius/src/markers.rs` — a small helper that parses a file, finds `>>> junius managed start` / `<<< junius managed end` blocks, replaces their contents, and re-serializes the file preserving non-managed regions byte-for-byte.

### `junius new plugin <name>`

Scaffolds a new plugin from a built-in template:
- `plugins/<name>/plugin.toml` — minimal manifest matching the hello example, with `name = "<name>"`.
- `plugins/<name>/Cargo.toml`.
- `plugins/<name>/src/lib.rs` — `plugin_metadata!()` + a `Plugin` impl with a single placeholder route.

After scaffolding, runs `junius sync` automatically.

### `dev/platform.toml`

```toml
[source]
path = "."

[plugins]
enabled = ["hello"]
```

(`[source].path = "."` is the dev convention from [../design/05-repository-and-deployment-layout.md](../design/05-repository-and-deployment-layout.md) §5.5. M03 doesn't enforce source resolution yet — M11 does. The `path = "."` declaration is honoured by treating the current dir as the source root, which is the only mode supported until M11.)

### Tests

- `plugins/hello/tests/hello.rs` — in-process Axum test calling `Plugin::routes(...)` directly with a stub `PluginResources`, asserting `/ping` returns `200 pong`.
- `platform/tests/boot_with_hello.rs` — full-binary integration test that runs the host (after `junius sync`) and curls `/h/hello/ping`.
- `tools/junius/tests/sync.rs` — snapshot-tests the generated `plugins.rs` and the `Cargo.toml` diff against the `valid-minimal` deployment fixture.

## Scope (out)

- No frontend route. `/p/hello` doesn't exist yet — M04 adds it.
- No RPC. M05 adds Connect-RPC.
- No DB, no permissions. M06+ layer those in.
- No git-URL `[source]` resolution. `[source]` is parsed but only `path = "."` is honoured until M11.
- No `junius plugin enable/disable`. Those edit `platform.toml` in a deployment dir; they're meaningful once M11's deployment workflow exists. Until then, edit `dev/platform.toml` by hand.

## Library choices — confirm with user before starting

| Choice | Proposed default | Rationale | Downstream milestones to update if changed |
|---|---|---|---|
| **Plugin's HTTP test client (in-process)** | `tower::ServiceExt::oneshot` against the plugin's `Router` | No HTTP server needed; fastest test loop | All backend milestones |
| **Plugin's HTTP test client (full-binary)** | `reqwest` against a `tokio` task hosting the bound socket | Mirrors real prod conditions | All backend milestones |
| **Marker-comment editing** | Custom helper inside `tools/junius/` (regex-based, ~50 LoC) | Avoids pulling in a TOML AST library when the markers + line-based replacement is sufficient | M05/M06/M11 — each adds new managed regions |
| **`workspace` protocol versions** | `[workspace.dependencies]` already chosen in M00/M02; nothing new here | — | — |

## Open questions resolved

- **Testing strategy** — locked at this milestone since it's the first place plugin test code lands.
  - Backend unit tests: `cargo test -p <plugin-crate>` using `tower::ServiceExt::oneshot`.
  - Backend integration tests: `cargo test -p platform` driving the full bound binary via `reqwest`.
  - FE unit tests: `vitest` + `@testing-library/react` (introduced for real at M04).
  - End-to-end browser tests: `playwright` against `junius dev` (introduced at M04).
  - Proto contract tests: `buf breaking` against `main` (introduced at M05).
  Updates: every later milestone's "Verify" block uses these tools.

## Verification

```bash
# Scaffold check (run from repo root)
target/release/junius new plugin demo
# → creates plugins/demo/, runs sync, prints "Plugin 'demo' scaffolded."
# Now remove it (we're testing the codegen path, not adding a real plugin):
rm -rf plugins/demo
# Re-edit dev/platform.toml back to enabled = ["hello"]

# Sync writes the generated file
target/release/junius sync --config dev/platform.toml
# → writes platform/src/generated/plugins.rs

# Confirm dry-run is idempotent
target/release/junius sync --config dev/platform.toml --dry-run
# → exits 0 (no changes pending)

# Build and run the host
cargo build -p platform
target/debug/platform &
PID=$!
sleep 0.5

# The route exists
curl -fsS http://127.0.0.1:8080/h/hello/ping
# → "pong"

# Cleanup
kill -INT $PID

# Disable hello, re-sync, re-build
# → /h/hello/ping should now 404
sed -i 's/enabled = \["hello"\]/enabled = []/' dev/platform.toml
target/release/junius sync --config dev/platform.toml
cargo build -p platform
target/debug/platform &
PID=$!; sleep 0.5
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/h/hello/ping
# → 404
kill -INT $PID

# Re-enable hello before moving on
sed -i 's/enabled = \[\]/enabled = ["hello"]/' dev/platform.toml
target/release/junius sync --config dev/platform.toml

# Test suites
cargo test -p hello-plugin
cargo test -p platform
cargo test -p junius
```

After this, the architecture's basic shape is observable: a manifest declares a plugin, `junius` composes the host, and the binary serves the plugin's routes.
