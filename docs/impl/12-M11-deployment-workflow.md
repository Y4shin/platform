## Reconciliation (as built)

The plan below is the design; the shipped implementation differs in a few spots:

- **Git resolution shells out to the `git` CLI** (in the nix dev shell), not the
  `gix` crate — lighter, and it reuses the user's existing git auth.
- **`platform.lock` content-hashes `path` sources too** (not just git). A
  consequence: the in-repo `examples/example-deployment/` points at the live
  monorepo via `path = "../.."`, so its lock would be perpetually stale — it's
  gitignored, and CI builds it with `--update-lock`.
- **The artifact is the host binary `juniusd`, copied to `<deployment>/platform`.**
- **`develop` gates only the command surface** (`new`/`sync`/`dev`), not the
  dependency tree: the dev commands share `tokio`/`regex` with end-user commands
  (`migrate` needs the tokio runtime; `build` reuses sync's generation), so no
  dependency actually drops out under `--no-default-features`.
- **`build` always builds release** (deployment artifacts are optimized).
- The source/cache/hash logic lives in the CLI (`blake3` stays out of the host +
  manifest); the lock **type** is pure serde in `junius-manifest`.
- Secret resolver: added `file:PATH`; `vault:` remains an explicit
  unsupported-scheme error (real Vault integration stays out of scope).

## Goal

A deployment lives in its **own directory**, outside the source monorepo, holding only `platform.toml`, `platform.lock`, and `secrets/`. `junius build` run from a deployment dir resolves `[source]` (git URL+rev or local path), generates composition glue against that source revision, builds, and outputs a self-contained binary. `platform.lock` pins the resolved revision; rebuilds fail unless the lock matches.

## Why now

Through M10, every developer workflow used `dev/platform.toml` *inside* the source monorepo. M11 makes the source/deployment split real, which the design treats as foundational ([../design/05-repository-and-deployment-layout.md](../design/05-repository-and-deployment-layout.md) §5.5). Doing this before M12's hardening means CI integration tests can drive `junius build` from a deployment dir, exactly as production will.

## Scope (in)

### Source-resolution flow

A deployment's `platform.toml`:

```toml
[source]
repo = "git+https://github.com/org/junius.git"
rev  = "v0.5.0"                       # branch, tag, or SHA

[plugins]
enabled = ["hello", "speakers"]

[plugins.hello]
# plugin-specific config

[config]
database_url = "env:DATABASE_URL"
oidc_issuer = "https://auth.example/application/o/platform/"
oidc_client_id = "platform"
oidc_client_secret = "env:OIDC_CLIENT_SECRET"
# etc., per M06 / M10 schema
```

`junius build`:

1. **Parse** `platform.toml` (manifest schema from M01 already supports `[source]`).
2. **Resolve `[source]`**:
   - If `repo = "git+..."` + `rev`: clone (or fetch in cached repo) under `~/.cache/junius/sources/<sha256-of-url+rev>/`.
   - If `path = "..."`: use directly (dev convention).
3. **Verify lock**: if `platform.lock` exists, the resolved source SHA must match `platform.lock` (unless `--update-lock`). Mismatch → exit non-zero with a clear "the source moved; run with --update-lock if intentional" message.
4. **Validate**: every plugin in `[plugins].enabled` exists in the resolved source's `plugins/` directory; manifests parse; deps resolve (uses M09's check).
5. **Generate composition glue** into a deployment-specific build dir under `~/.cache/junius/builds/<deployment-hash>/`:
   - `platform/src/generated/plugins.rs` — same shape as M03, but written into the build dir's working copy.
   - `platform/frontend/src/generated/routes.ts` — from M04.
   - `platform/frontend/src/generated/component-registry.ts` — from M09.
   - Patched `Cargo.toml` + `package.json` between markers — pointing at the resolved-source plugin crates/packages.
   - `[config]` resolved (env-var indirection expanded) and written into a JSON file the host loads at boot. (Or kept as `platform.toml` and loaded directly at runtime — the latter is simpler.)
6. **Build**: invoke the same `cargo build --release -p platform` + `pnpm build` + `rust-embed` pipeline from M04, but from the resolved-source working copy.
7. **Output**: copy the binary to `./platform` in the current dir (the deployment dir). Print build summary.

### `platform.lock`

Format: TOML. Records the **resolved** revision and source content hash.

```toml
# Generated by junius — do not edit.
[source]
url = "git+https://github.com/org/junius.git"
resolved_rev = "a1b2c3d4e5f6..."         # the full commit SHA
content_hash = "blake3:..."               # blake3 of the source tree (excluding .git)

[plugins]
# Hash of each enabled plugin's manifest + source tree
hello    = "blake3:..."
speakers = "blake3:..."
```

Strict mode (default): `junius build` fails if `content_hash` differs from what the resolved source produces.

`--update-lock` mode: rewrites `platform.lock` with the new hashes and proceeds. Equivalent to `cargo update` discipline.

### Source cache

Layout under `~/.cache/junius/`:

```
~/.cache/junius/
├── bin/                                  # vendored binaries (buf from M05)
│   └── buf-1.50.0
├── sources/
│   ├── <hash1>/                          # one source revision = one cached dir
│   │   ├── .git/
│   │   └── (workspace contents)
│   └── <hash2>/
└── builds/
    └── <deployment-hash>/                # per-deployment build outputs
```

Cache eviction (manual for v1): `junius cache prune` deletes anything not touched in N days (default 30).

### Secret loading

`[config]` values may be:
- Literal strings → used as-is.
- `env:VAR` → read from environment at boot (and on every `[config]` lookup; lets ops rotate without restart for non-critical config).
- `file:PATH` → read from a file (useful for K8s secrets mounted as files).
- `vault:PATH` — deferred to v2.

The resolver lives in `crates/junius-sdk/src/config.rs`. Plugin code calls `resources.config.get::<T>("key")`; the resolver expands the indirection transparently.

### Plugin enablement commands

`junius plugin enable <name>` (run from a deployment dir):
1. Verify the plugin exists in the resolved source.
2. Verify all required deps are enabled (or are enabled together).
3. Edit `platform.toml`'s `[plugins].enabled` to include the name.
4. Run `junius sync` (now writes into the cached source's working copy).
5. Print a summary of what changed.

`junius plugin disable <name>`:
1. Check no other enabled plugin requires it (required deps).
2. Remove from `[plugins].enabled`.
3. Sync.

### Developer-only command gating (`develop` cargo feature)

The CLI stays a **single binary**, but commands that only make sense inside the
source monorepo are gated behind a `develop` cargo feature, so an end-user
deployment build ships a CLI without scaffolding/dev clutter (and without the
heavier dev-only dependency tree those commands pull in).

- **`develop` is a default feature.** Working in the source tree (`cargo build`,
  `cargo run -p junius`) gets the full CLI. The deployment build path
  (`junius build`, and the example-deployment CI job) compiles the bundled CLI
  with `--no-default-features` (plus whatever runtime features it needs), so the
  shipped artifact only carries end-user commands.
- **End-user commands (always compiled):** `check`, `build`, `migrate`
  (up/status — deployments run migrations), `plugin` (enable/disable/list/info),
  plus the future `cache prune` / `--check-config`. These are what operating a
  deployment requires.
- **Developer-only commands (gated behind `develop`):** `new` (scaffolding new
  plugins/migrations/components/rpc/permissions), `sync` (in-source composition
  glue), `dev` (Vite dev server + hot reload). Their *logic* that other commands
  reuse (e.g. the composition-glue generation `plugin enable` calls) stays
  compiled — only the user-facing subcommand entry points are `#[cfg(feature =
  "develop")]`.
- **Mechanism:** `#[cfg(feature = "develop")]` on the gated `Command` enum
  variants and their dispatch arms, and `#[cfg(not(feature = "develop"))]`
  fallbacks are unnecessary (clap just won't know the subcommand). Keep the
  feature wiring in `tools/junius/Cargo.toml`; move the dev-only deps
  (e.g. the Vite/`dev` plumbing) under `optional = true` + the feature so a
  deployment CLI doesn't compile them.
- **Verify:** `cargo build -p junius` exposes `new`/`sync`/`dev`;
  `cargo build -p junius --no-default-features` does not (the binary rejects
  `junius dev` with an unknown-subcommand error), while `build`/`migrate`/
  `plugin`/`check` still work.

### Example deployment

A new directory committed inside the source monorepo under `examples/example-deployment/`:

```
examples/example-deployment/
├── platform.toml                         # uses [source].path = "../.." for dev
├── platform.lock                         # generated on first build
├── README.md                             # walks through running it
└── .gitignore                            # ignores ./platform binary + secrets/
```

This is **not** a workspace member — it lives sibling-style inside the repo solely to give a CI-runnable example. Real deployments live in separate repos.

### CI integration

`.github/workflows/ci.yml` gains a job:

```yaml
- name: Build example deployment
  run: |
    cd examples/example-deployment
    ../../target/release/junius build
    file ./platform                         # binary exists
    # Smoke test: boot against an ephemeral postgres
    ./platform --check-config
```

`junius ... --check-config` is a no-network self-check: parses `platform.toml`, validates everything resolvable without an actual DB, exits 0. Used to catch deployment-config typos.

## Scope (out)

- No submodule-based plugin composition resolution. Submodules already work because they appear under `plugins/<name>/` in the resolved source — `junius` doesn't need special handling. (The git library does need to honour `--recurse-submodules` when cloning.)
- No multi-source resolution (different plugins from different repos). Single `[source]`.
- No remote binary cache (sccache, cargo-binstall registry). Build is from-source.
- No reproducible-build guarantees beyond what cargo/pnpm/buf already provide.
- No deployment-secret encryption at rest — secrets live in `secrets/` (gitignored) or as env vars from a deployment-host mechanism (K8s secrets, systemd `EnvironmentFile`, etc.).

## Library choices — confirm with user before starting

| Choice | Proposed default | Rationale | Downstream milestones to update if changed |
|---|---|---|---|
| **Git library (Rust)** | `gix` — pure-Rust, no system git dep | Avoids developer setup friction | If `gix` lacks an auth scheme we need (e.g. SSH key formats), fall back to shelling out to `git` |
| **Source content hashing** | `blake3` | Fast, parallel-friendly | — |
| **Source cache root** | `~/.cache/junius/` (XDG-compliant) | Standard | — |
| **Build artifact name** | `platform` (placed in the deployment dir, never overwritten without `--force`) | Consistent across deployments | — |
| **`--update-lock` semantics** | Like `cargo update`: rewrites the lock and proceeds | Familiar mental model | — |
| **`junius plugin enable` writes back to `platform.toml`** | Yes — with marker comments preserving developer edits | Same marker-comment policy from M03 | — |

## Verification

```bash
# Build the example deployment in-tree
cd examples/example-deployment
../../target/release/junius build
ls -lh ./platform                              # the binary exists
file ./platform                                # ELF executable
cat platform.lock                              # contains resolved_rev + content_hash

# Strict-mode lock enforcement
echo "garbage" >> /tmp/source-corruption        # (don't really do this — concept demo)
# touching the working copy would change the content_hash; junius build should refuse:
../../target/release/junius build
# → "platform.lock content_hash does not match resolved source. Run with --update-lock if intentional."

# Update lock
../../target/release/junius build --update-lock
# → succeeds; new content_hash recorded

# Out-of-tree deployment dir
TMP=$(mktemp -d)
cp examples/example-deployment/platform.toml "$TMP/"
sed -i 's|path = "../.."|path = "/absolute/path/to/junius"|' "$TMP/platform.toml"
cd "$TMP"
~/junius/target/release/junius build
./platform &
# Boots, connects to a fresh test DB, serves the platform.

# Plugin enable / disable
../../target/release/junius plugin enable widgets
diff platform.toml platform.toml.bak           # widgets added to enabled

../../target/release/junius plugin disable widgets
# → refuses if anything else depends on widgets; otherwise removes it.

# `--check-config` (CI's smoke test)
./platform --check-config                       # parses, validates, exits 0
DATABASE_URL=garbage ./platform --check-config  # parses literal env, exits 0 (URL not connected)

# Cache pruning
../../target/release/junius cache prune --older-than 0d
ls ~/.cache/junius/sources/                    # emptied

# Tests
cargo test -p junius --test build_e2e
# Drives `junius build` against a fixture deployment dir + verifies the resulting
# binary boots and serves the hello plugin's routes.
```

After M11, the source vs. deployment split is real. The codebase doesn't know which plugins ship; deployments declare it. The artifact is a single binary.
