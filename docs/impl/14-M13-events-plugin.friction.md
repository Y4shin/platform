# M13 — Plugin-authoring friction log

Living record of every friction point hit while building the `events` plugin
(the first real domain plugin), captured as we go for a **joint triage at the
end of M13**. Append-only; one row per annoyance.

- **Severity:** `blocker` (had to work around to proceed) · `friction` (slowed
  authoring) · `papercut` (minor) · `wish` (nice-to-have).
- **Proposed fix:** concrete enough for triage to scope directly.

**Mid-M13 triage (2026-05-25):** the `junius new`/`sync` workflow cluster
("Cluster A" — rows tagged Stage 1) is being **fixed in M13 Stage 4** (`new`
becomes scaffold-only and needs no `platform.toml`, since dev-facing commands
that don't deploy an instance shouldn't require a deployment config; `sync`
fully wires a plugin: buf.yaml + buf generate, host frontend workspace dep,
rustfmt-clean output, backend-only opt-out). The SDK/host-ergonomics + Groups
authorization + FE redirect items (rows tagged Stage 2/3, B/C/D) are folded into
**M13 Stage 5** (pulled forward *before* the domain build so the events plugin
calls the final `Groups` API once, not twice — C is the one the plugin actually
consumes; B/D are host/SDK-internal but cheap to finalize alongside). Constraint:
the `PluginResourceCtx` fix (B) must be **compile-time-checked** — a named-field
**struct literal**, not a builder. The two "fixed this stage" rows (group
directory, public routes) are done.

| 2026-05-25 | 1 | new / sync | `junius new plugin events` auto-runs `sync` with the default `platform.toml` (cwd), which doesn't exist in this repo (dev config is `dev/platform.toml`) → prints `cannot read platform.toml` and **exits 1** despite scaffolding succeeding. | 2026-05-25 | 1 | new | Scaffold emits only `plugin.toml` + `Cargo.toml` + `src/lib.rs` (a `/ping` route). | 2026-05-25 | 1 | sync | Enabling a plugin requires a **frontend package** too — the generated `routes.ts` unconditionally `import`s `buildRoutes` from `@junius/plugin-<name>`, so a backend-only plugin fails `pnpm typecheck` until you hand-create `frontend/{package.json,tsconfig.json,src/index.ts,routes/...}`. | 2026-05-25 | 1 | sync | `junius sync` emits Rust (`platform/src/generated/*.rs`) that is **not rustfmt-formatted** (single-line tuples), so `cargo fmt --check` fails after every sync — you must run `cargo fmt` afterward and commit the reformatted generated files. (Same class as the M11 `cross_check` nit.) | papercut | `sync` should run `rustfmt` on emitted Rust (or emit already-formatted code) so generated files are fmt-clean as written. |
| 2026-05-25 | 1 | sync | Enabling a plugin also requires manually adding `"@junius/plugin-<name>": "workspace:*"` to `platform/frontend/package.json` (+ `pnpm install`) — sync emits the `routes.ts` import but not the workspace dependency, so host typecheck fails with `Cannot find module '@junius/plugin-events'`. | friction | `sync` should add/remove the host frontend's `workspace:*` dep for each enabled plugin (it already rewrites `platform/Cargo.toml` deps for the Rust side). |

| 2026-05-25 | 1 | proto/build.rs | Adding a plugin with a proto requires **manually** (a) appending `plugins/events/proto` to the workspace `buf.yaml` `modules:` and (b) running `pnpm exec buf generate` to emit the TS `*_pb.ts`. | 2026-05-25 | 2 | sdk-groups | The SDK exposed **no group directory** — a plugin could see only the *current user's* `memberships`, with no way to enumerate a group's members (needed for group sign-up pre-fill) or resolve a group by name (needed for `/ics/g/<name>`). Fixed this stage by adding a `Groups` accessor (`by_name`/`by_id`/`members`). | blocker | (Done in M13) `Groups` on `PluginResources`, on the platform pool like `Users` (no new grants). |
| 2026-05-25 | 2 | sdk-groups | `Groups` runs on the **platform pool**, so any plugin can enumerate **any** group's full roster + emails and resolve any group name — there's no per-call authorization (extends the existing `Users` trust model, but `members()` is more sensitive). | wish | Add an authorization-checked variant `members(group, as_caller)` (caller must be a member / hold a permission), or gate behind a `directory.groups` capability. |
| 2026-05-25 | 2 | sdk | `PluginResourceCtx::new` is a **13-positional-argument** constructor; adding one host handle (`Groups`) silently breaks every direct caller (e.g. `hello/tests/send_greeting.rs`) with an arg-count error and an `#[allow(too_many_arguments)]`. | papercut | A builder (`PluginResourceCtx::builder()...`) or struct-update from `Default`, so adding handles is non-breaking and self-documenting. |
| 2026-05-25 | 2 | sdk-groups / manifest | `platform.group.name` has **no unique constraint** (migration 0003), so `Groups::by_name` is ambiguous (returns earliest-created). | 2026-05-25 | 3 | public-routes | The SPA had **no login-optional route** mechanism — `AuthProvider` redirected to login before the router rendered, so a public page (the invite surface) was impossible. | 2026-05-25 | 3 | public-routes | There are **two** redirect-to-login paths — `AuthProvider`'s `/api/me` handler *and* `queryClient.onError` on any `Code.Unauthenticated` RPC — and both had to be taught the public-path allowlist independently. | 2026-05-25 | 6 | authz | **No `record_owner` counterpart for delete.** `Authz` records ownership on create but offers no `forget_owner(kind, id)` / `forget_resource`, and `platform.resource_principal` has no FK to the plugin's row (the resource lives in the plugin schema), so deleting an event **orphans** its `resource_principal` (and any `resource_share`) rows. Worked around by just deleting the event row; the ACL rows leak. | friction | Add `authz.forget_resource(kind, id)` (deletes resource_principal + resource_share in the caller's tx) and call it from `EventRepo::delete`; document it as the delete-time counterpart to `record_owner`. |
| 2026-05-25 | 6 | authz / repo-macro | **Group-owned reads need a role that grants the permission, not just membership.** `platform.user_can_access` step 2 requires the member's role to hold `events:read` via `platform.role_permission` — a group member whose role lacks the plugin's permission can't see the group's events. Correct + secure, but non-obvious while authoring (cost a test failure to discover); easy for an author to assume "member ⇒ can see group resource". | papercut | Document the group-ownership access rule prominently in the authoring guide (the `record_owner(Group)` + `role_permission` interaction), ideally with the worked events example. |
| 2026-05-25 | 6 | repo-macro / sqlx | **Custom-enum `query!` ergonomics.** Postgres enum columns force `col AS "col: Type"` overrides on every SELECT (so `e.*` is unusable — every column must be spelled out) and `$N::events.<enum>` casts on INSERT/UPDATE binds, or sqlx can't infer the param type. A lot of boilerplate for two enum columns. | papercut | A repo-macro helper or doc snippet for enum columns; or guidance to spell columns explicitly. At minimum, cover the `AS "col: Type"` + `$N::schema.enum` pattern in the authoring guide. |
| 2026-05-25 | 6 | proto/build.rs | **No shared `Empty` response.** buf `STANDARD` lint (`RPC_RESPONSE_STANDARD_NAME`) forbids reusing one `Empty` message across RPCs — each method needs a uniquely named response (`DeleteEventResponse {}`), even when empty. Mild surprise for authors used to `google.protobuf.Empty`. | papercut | Document the per-RPC response-naming convention in the authoring guide; or relax the lint for a shared empty type. |
| 2026-05-25 | 6 | repo-macro / sync | **`use junius_sdk::permissions` collides with the generated module.** Importing the `permissions!` macro by bare name clashes with `plugin_metadata!()`'s generated `pub mod permissions`, yielding a confusing `E0255 permissions redefined` **plus** cascading `no EventsRead in permissions` errors. The fix (use the fully-qualified `junius_sdk::permissions!(...)`) isn't obvious from the error. | papercut | Note the gotcha in the authoring guide, or have the macro emit the witness module under a name that can't collide with the macro import. |
| 2026-05-25 | 7 | repo-macro / authz | **No documented "public/ungated handler" pattern.** The public invite surface (GetInvite/Signup/OptOut — risk #4) needs two non-obvious moves: (a) ungated repo methods in a **plain `impl<P>` block** (no `#[impl_repository]`, no `Has` bound) so they're callable on `Repo<()>` while still using the macro's inherent `pool()/user()/audit()`; and (b) handlers that build `Ctx::<()>::from_rpc(&ctx)` — the **`()` no-permission witness** — to obtain the *real* (maybe-anonymous) caller without a permission check, letting the SQL `visibility='public' OR user_can_access(...)` predicate do the access control. It works cleanly with zero new platform features, but nothing documents it. | friction | Document the public-handler pattern (plain-impl ungated methods + `Ctx::<()>` + ACL-in-SQL) as a first-class section of the authoring guide; consider an SDK helper that names the intent (e.g. `Ctx::public(&ctx)`). |
| 2026-05-25 | 7 | proto/build.rs | **No clean nullable scalar on the wire.** proto3 field-presence (`optional`) isn't used anywhere in the repo, so `slot_limit` uses a `0 = unlimited` **sentinel** rather than a real null. Works (the DB CHECK forbids 0), but it's a foot-gun for the next nullable int. | papercut | Decide a convention: adopt proto3 `optional` (confirm buffa support) or document the sentinel pattern in the guide. |
| 2026-05-25 | 7 | proto/build.rs | **Nested-message request fields untested → flattened.** Reading a nested message (e.g. an `InviteConfig`) out of a generated `Owned…RequestView` isn't demonstrated by any existing plugin, so the invite config was **flattened** into scalar fields on Create/UpdateInviteRequest to stay on the proven path. Bloats the request messages. | wish | Verify + document nested-message handling in `Owned…View`s, or provide an example, so configs can be grouped. |
