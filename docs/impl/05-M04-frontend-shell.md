# M04 — Frontend Shell + `buildRoutes` + Vite + `rust-embed`

> **Status:** ✅ Implemented — see commit `M04: frontend shell + Vite + rust-embed + junius dev/build` in `git log`.

## Goal

A React+TanStack frontend shell composed from the `hello` plugin's `buildRoutes`. `junius dev` runs Vite + the Axum host concurrently with `/h/*` proxied through. `junius build` produces a single binary embedding the FE bundle via `rust-embed`. Visiting `/p/hello` in a browser renders the plugin's page.

## Why now

The backend's plugin composition (M03) works end-to-end. M04 mirrors that on the frontend so we have a complete UI-and-server slice before introducing RPC (M05) or persistence (M06). It also forces validation of the "code-based TanStack routing composes plugin route subtrees" claim from [../design/04-frontend.md](../design/04-frontend.md) §4.2 in real running code.

import { Route, type AnyRoute } from '@tanstack/react-router';
import { HelloPage } from './pages/HelloPage';

export function buildRoutes(parent: AnyRoute) {
  return [
    new Route({
      getParentRoute: () => parent,
      path: '/',
      component: HelloPage,
    }),
  ];

`HelloPage.tsx` calls `/h/hello/ping` via `fetch` and renders the response, just to prove the proxy works. (Connect-Query arrives in M05.)

### `junius sync` extensions

- Writes `platform/frontend/src/generated/routes.ts` from the enabled plugins (using their `route_prefix` from manifests + a convention import from `@junius/plugin-<name>`).
- Writes `platform/frontend/src/generated/component-registry.ts` (empty at M04).
- Updates `platform/frontend/package.json` between markers to add deps on each enabled plugin's FE package:
  ```json
  // >>> junius managed start
  "@junius/plugin-hello": "workspace:*"
  // <<< junius managed end
  ```
- Updates `tailwind.config.ts` `content` paths between markers to include every enabled plugin's `frontend/src/**/*.{ts,tsx}`.

### `junius build` extensions

The full production pipeline:

1. `junius sync` (idempotent).
2. `cargo build --release -p platform` (Rust).
3. `pnpm --filter @junius/shell build` (Vite → `platform/frontend/dist/`).
4. Run a second pass of `cargo build --release -p platform` with the `embed-frontend` feature on so `rust-embed` picks up `platform/frontend/dist/`. (Two cargo passes is fine here — the FE bundle is `include_dir!`'d at compile time, not linked dynamically.)
5. Output: `target/release/platform` is the deployment artifact.

`platform/src/server.rs` adds a fallback handler that, when the `embed-frontend` feature is on, serves embedded FE assets, falling back to `index.html` for SPA routes.

### `junius dev` first version

```rust
// tools/junius/src/commands/dev.rs (sketch)
async fn run_dev() -> Result<()> {
    // 1. junius sync (idempotent first run)
    // 2. spawn vite via `pnpm --filter @junius/shell dev`
    // 3. spawn cargo via `cargo run -p platform`
    // 4. tokio::select! waits for either to die + Ctrl-C
    //    file watching, proto regeneration, manifest re-sync land in M05/M06
}
```

For M04, `dev` only handles the Vite + cargo split; hot manifest sync + buf regen come later (M05/M06).

## Scope (out)

- No HMR across plugin boundaries — the design's open question is *validated* during M04 but not solved until needed. If pnpm symlinks + Vite give clean HMR out of the box (likely), nothing more needed. If they don't, the fallback (per-plugin Vite build or module federation) is deferred to a later milestone.
- No login/logout flow. `AuthProvider` stubs an always-authenticated user.
- No RPC. `HelloPage` uses raw `fetch`. M05 swaps it to Connect-Query.
- No real component registry usage. The registry exists but is empty.
- No production embedding test against a deployment dir. M11 covers that.

## Library choices — confirm with user before starting

| Choice | Proposed default | Rationale | Downstream milestones to update if changed |
|---|---|---|---|
| **React version** | Latest stable React (19 if available at impl time, else 18) | Best ecosystem support; design names no version constraint | Every FE milestone |
| **TanStack Router + Query** | Latest stable | Locked by design ([../design/04-frontend.md](../design/04-frontend.md) §4.1) | Every FE milestone |
| **Vite** | Latest stable | Locked by design | Every FE milestone |
| **Styling** | `tailwindcss` v4 + `@radix-ui/react-*` wrapped by `@junius/design` | Locked by design ([../design/12-frontend-plugin-interface.md](../design/12-frontend-plugin-interface.md) §12.9) | Every FE milestone |
| **FE unit tests** | `vitest` + `@testing-library/react` + `jsdom` env | Standard React testing stack | Every FE milestone |
| **E2E browser tests** | `playwright` against `junius dev` | Real browser, real bundle, real proxy | Every FE milestone |
| **Embedder (Rust)** | `rust-embed` | Locked by design; `include_dir!`-like ergonomics | M11 (deployment pipeline) |
| **Dev process supervisor (inside `junius`)** | Custom small implementation: `tokio::process::Command` + `tokio::select!` | Total code ~100 LoC; avoids a new dep | M05/M06 — both extend `dev` with more child processes |
| **Asset handling** | Per-plugin assets under `plugins/<name>/frontend/src/assets/`, imported via Vite (URL or inline); bundled into the FE artifact | Single artifact, no per-asset hosting; resolves the open question | M13 (Speakers may have illustrative assets) |

## Open questions resolved

- **Asset handling** — per-plugin assets are Vite-imported; resolved as above.
- **Hot reload across plugin boundaries** — validated during M04. If pnpm symlinks give clean HMR (expected), this question closes. If not, log the gap and pick a fallback at the next milestone touching FE (M05 likely).
