# M09 — Cross-Plugin Composition (2-Plugin Demo)

## Goal

Two new plugins exercise every cross-plugin mechanism: `greetings` declares a **required** dep on `hello` (uses its `greeting_template` table, calls its `Greet` RPC, imports its `GreeterCard` component); `widgets` exposes a `VenuePicker` that `greetings` uses as an **optional** dep via the typed component registry. Per-plugin narrow `rpc` namespaces are generated; cross-plugin Postgres grants applied; every `junius check` cross-plugin rule enforced.

## Why now

Cross-plugin composition is the design's central conceit. Validating it requires more than one plugin. Doing it now — before the infra capabilities (M10) and the first real plugin (M13) — surfaces gaps in the codegen and check tooling early.

## Scope (in)

### `plugins/hello/` — extensions

Make `hello` *exposable*:

```toml
# plugin.toml additions
[exposes.components.GreeterCard]
module      = "./frontend/lib/GreeterCard"
description = "Renders a greeting with the speaker's name."

[exposes.tables.greeting_template]
schema      = "hello"
description = "Stable canned greeting templates."
```

`plugins/hello/migrations/0003_greeting_template.up.sql`:

```sql
CREATE TABLE hello.greeting_template (
    id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name  TEXT NOT NULL UNIQUE,
    body  TEXT NOT NULL
);
INSERT INTO hello.greeting_template (name, body) VALUES
    ('default', 'Hello, {name}!'),
    ('formal',  'Greetings, {name}.');
```

`plugins/hello/frontend/src/lib/GreeterCard.tsx` — the exposed component.

### `plugins/greetings/` — new plugin (required dep on hello)

```toml
# plugins/greetings/plugin.toml
[plugin]
name = "greetings"
display_name = "Greetings"
manifest_schema = 1

[dependencies.hello]
optional     = false
tables       = ["greeting_template"]
rpc_methods  = ["HelloService.Greet"]

[dependencies.widgets]
optional     = true                       # graceful degradation
# (no tables / rpc_methods declared — UI dep only)

[permissions]
"greetings:read"  = "View greetings."
"greetings:write" = "Create greetings."
```

`plugins/greetings/migrations/0001_greeting.up.sql`:

```sql
-- @requires hello:0003_greeting_template
CREATE TABLE greetings.greeting (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    template_id  UUID NOT NULL REFERENCES hello.greeting_template(id),
    recipient    TEXT NOT NULL,
    venue_id     UUID NULL,             -- optional dep: nullable
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Rust source uses `hello`'s table via SQL JOINs (the role grant lets `role_greetings` SELECT/INSERT on `hello.greeting_template`), and consumes the hello plugin's component on the FE:

```tsx
// plugins/greetings/frontend/src/routes/pages/GreetingFormPage.tsx
import { GreeterCard } from '@junius/plugin-hello';        // required dep → ES import
import { rpc } from '@junius/generated/greetings';
import { getComponent } from '@junius/sdk';

export function GreetingFormPage() {
  const VenuePicker = getComponent('widgets.VenuePicker');   // optional → may be undefined

  return (
    <Stack gap="md">
      <GreeterCard name="World" />
      {VenuePicker
        ? <VenuePicker value={venueId} onChange={setVenueId} />
        : <input value={venueText} onChange={e => setVenueText(e.target.value)} placeholder="Venue (free text)" />}
    </Stack>
  );
}
```

### `plugins/widgets/` — new plugin (optional dep target)

Minimal — exposes one component, has no other plugin-facing surface.

```toml
[plugin]
name = "widgets"
display_name = "Widgets"
manifest_schema = 1

[exposes.components.VenuePicker]
module      = "./frontend/lib/VenuePicker"
description = "Picks a venue from a small in-memory list."

[permissions]
"widgets:read" = "View venues."
```

The picker is intentionally simple — no DB, no RPC, just a static array. The point is to exercise the optional-dep mechanism, not to model real venues.

### Narrow per-plugin RPC namespace

For each enabled plugin, `junius sync` generates `packages/generated/src/plugins/<plugin>/rpc.ts` exposing **only** the methods declared in:
- Its own services.
- Its `[dependencies.<dep>].rpc_methods` declarations.

For `greetings`:

```ts
// Generated by `junius sync` — do not edit.
import { GreetingService_CreateGreeting, GreetingService_ListGreetings }
    from '../../proto/greetings/v1/greetings_connect';
import { HelloService_Greet }
    from '../../proto/hello/v1/hello_connect';

export const rpc = {
  GreetingService: {
    createGreeting: GreetingService_CreateGreeting,
    listGreetings:  GreetingService_ListGreetings,
  },
  HelloService: {
    greet: HelloService_Greet,
    // listGreetings, createGreeting, etc. — absent. The TS type can't reach them.
  },
} as const;
```

A plugin that hasn't declared `HelloService.Greet` in its manifest's `rpc_methods` cannot import it from its narrow namespace (compile error: `rpc.HelloService is undefined` at the type level).

### Component registry

`packages/sdk/src/registry/getComponent.ts` becomes properly typed:

```ts
import type { ComponentRegistry } from '@junius/generated/component-registry-types';

export function getComponent<K extends keyof ComponentRegistry>(key: K): ComponentRegistry[K];
export function getComponent<K extends string>(key: K): ComponentType | undefined;
```

`junius sync` writes two files:
- `platform/frontend/src/generated/component-registry.ts` — the actual runtime registry.
- `packages/generated/src/component-registry-types.ts` — the type-level mapping per consumer.

```ts
// platform/frontend/src/generated/component-registry.ts
import { GreeterCard }  from '@junius/plugin-hello';
import { VenuePicker } from '@junius/plugin-widgets';

export const componentRegistry = {
  'hello.GreeterCard':   GreeterCard,
  'widgets.VenuePicker': VenuePicker,
} as const;
```

When `widgets` is disabled in `platform.toml`, the registry omits its entries; `getComponent('widgets.VenuePicker')` returns `undefined`.

### Cross-plugin Postgres grants

For `greetings` declaring `[dependencies.hello].tables = ["greeting_template"]`, `junius migrate` emits:

```sql
GRANT USAGE ON SCHEMA hello TO role_greetings;
GRANT SELECT, INSERT, UPDATE, DELETE ON hello.greeting_template TO role_greetings;
```

A query against `hello.greeting` (not exposed) from `role_greetings` returns a Postgres `permission denied`.

### `junius check` extensions

New rules enabled at this milestone:

1. **Cross-plugin RPC use matches manifest.** Scan `@junius/generated/<other>/rpc` imports + literal method-name references; every method used must appear in `[dependencies.<other>].rpc_methods`.
2. **Cross-plugin SQL references have a matching `-- @requires`.** Scan each migration for `<schema>.<table>` references where `<schema>` is another plugin's schema; require `-- @requires <schema>:<migration>` for the migration that created that table.
3. **Cross-plugin FK nullability.** FKs into an optional-dep schema must be nullable; required-dep FKs may be NOT NULL.
4. **No `CASCADE` on cross-plugin FKs.** Reject any `ON DELETE CASCADE` / `ON UPDATE CASCADE` clause where the referenced schema is another plugin's.
5. **Manifest dep matches usage.** Imports from `@junius/generated/<other>` (TS) or `<other>::` paths (Rust) must have a matching `[dependencies.<other>]` in the manifest.

Rule (2) requires migration parsing — uses `sqlparser-rs` (Postgres dialect). Rules (1), (5) use regex + glob across plugin source trees.

### Updated `dev/platform.toml`

```toml
[plugins]
enabled = ["hello", "greetings", "widgets"]
```

Disabling `widgets` and re-running `junius sync && junius build` produces a binary where `getComponent('widgets.VenuePicker')` returns `undefined` and the FE falls back gracefully.

## Scope (out)

- No more than two plugins beyond `hello`. Real domain plugins arrive in M13.
- No "private tables" leak detection inside `junius check` (a plugin reading a non-exposed cross-plugin table). The Postgres role grant fails at runtime; M12's full hardening adds the static check.
- No automatic dep version negotiation. Single-version monorepo.

## Library choices — confirm with user before starting

| Choice | Proposed default | Rationale | Downstream milestones to update if changed |
|---|---|---|---|
| **SQL parser for migration analysis** | `sqlparser-rs` (PostgreSQL dialect) | Pure Rust, decent dialect support | M12 (full schema-evolution rules use the same parser) |
| **TS import scanner** | Custom scan (regex over `import` statements) inside `junius check` | Lightweight; full-TS parsing isn't needed for the patterns we're checking | M12 |
| **Rust import scanner** | `syn` parse of each plugin's source tree (already in workspace) | Already a dep; gives accurate path resolution | M12 |
| **Component registry shape** | `as const` object literal + auto-generated type union | Locked by design ([../design/08-cross-plugin-composition.md](../design/08-cross-plugin-composition.md) §8.2) | — |

## Verification

```bash
# Scaffold the two new plugins
target/release/junius new plugin greetings
target/release/junius new plugin widgets
# (Manually edit their plugin.toml + write the source code per the design above.
#  Then re-sync.)

# Sync, migrate, build
target/release/junius sync --config dev/platform.toml
target/release/junius migrate up --config dev/platform.toml
target/release/junius build

# Functional test: with widgets enabled
target/release/junius dev --config dev/platform.toml &
# Browser: /p/greetings → form renders <VenuePicker> from widgets

# Disable widgets, re-sync, restart
sed -i 's/"widgets",//' dev/platform.toml
target/release/junius sync --config dev/platform.toml
target/release/junius migrate up --config dev/platform.toml  # widgets schema still exists (always-apply)
# kill dev process, restart
# Browser: /p/greetings → form renders the free-text fallback <input>
# Type-check still passes; the narrow rpc namespace for greetings doesn't change.

# Cross-plugin RPC narrowing — type-check confirms unauthorized methods are not in scope
# (Edit plugins/greetings/frontend/src/routes/pages/X.tsx to call rpc.HelloService.createGreeting.)
pnpm --filter @junius/plugin-greetings exec tsc --noEmit
# → error: Property 'createGreeting' does not exist on type ...

# Postgres role grant check
PGUSER=role_greetings psql -c "SELECT * FROM hello.greeting_template LIMIT 1;"   # → OK (exposed)
PGUSER=role_greetings psql -c "SELECT * FROM hello.greeting LIMIT 1;"            # → ERROR: permission denied

# junius check failures
# (1) Remove the @requires line from greetings/migrations/0001
target/release/junius check
# → "cross-plugin reference to hello.greeting_template at .../0001 lacks @requires hello:0003_greeting_template"

# (2) Add a CASCADE on a cross-plugin FK
# → "cross-plugin FK references with CASCADE are not allowed"

# (3) Try a NOT NULL FK into a widgets schema (optional dep)
# → "cross-plugin FK targeting optional dep 'widgets' must be nullable"

# Re-enable widgets for downstream milestones
sed -i 's/enabled = \["hello", "greetings"\]/enabled = ["hello", "greetings", "widgets"]/' dev/platform.toml
target/release/junius sync --config dev/platform.toml

# Tests
cargo test -p greetings-plugin
cargo test -p widgets-plugin
cargo test -p platform
pnpm --filter @junius/plugin-greetings test
pnpm exec playwright test                       # E2E flips widgets enable/disable and verifies UI behaviour
```

After M09, every cross-plugin mechanism described in the design has running code behind it.
